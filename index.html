claude-rooms

Rooms for Claude Code agent teams: a lead, workers, decision cards on a phone page, and a record in plain markdown.

The idea

A room is one project. It has:

  • a lead, a Claude Code session that plans the work, starts workers, keeps the record and asks you what only you can decide;
  • workers, background Claude Code sessions that each do one item in their own git worktree;
  • you, the owner, answering decision cards on a phone page or in chat;
  • a record: plain markdown files in a git repo of their own (~/rooms), which outlive every session.

The record is the memory, not any conversation. A lead can be a long-lived session you talk to, or a short one-shot turn started for a batch of events. Both read the same files and act the same way.

Most of the rules live in the rooms command, not in prompts: it refuses to start build work before a feature's PRD is agreed, refuses to mark an item done without a result and a successor, and decides which questions reach you.

Install

You need Node 24 or newer, git, and Claude Code.

git clone https://github.com/mvexel/claude-rooms ~/dev/claude-rooms
~/dev/claude-rooms/cli/rooms.ts install   # links `rooms` into ~/.local/bin
rooms init                                 # creates ~/rooms, the records repo

Install the plugin for all your sessions. At a Claude Code prompt:

/plugin marketplace add ~/dev/claude-rooms
/plugin install rooms@mvexel-rooms

Or from a shell: claude plugin marketplace add ~/dev/claude-rooms and claude plugin install rooms@mvexel-rooms --scope user. Sessions that are already open pick it up with /reload-plugins.

The page server

rooms serve runs the phone page and a sweep every 15 seconds that delivers events, applies due defaults and commits the record. Run it as a user service:

cp ~/dev/claude-rooms/deploy/claude-rooms.service ~/.config/systemd/user/
systemctl --user enable --now claude-rooms

To reach the page from your phone over Tailscale, set ROOMS_USERS to your Tailscale login in the unit first (only those logins can answer; the server refuses to listen beyond loopback without it), then:

tailscale serve --bg --set-path /rooms http://127.0.0.1:8787

Optional: add a git remote to ~/rooms. Commits are then mirrored in the background; nothing waits on a push.

Your first room

  1. Ask for it. In any Claude Code session: “Start a room for the export feature.” The session loads the lead skill and becomes the room's lead: rooms new export "CSV export" --feature. Use --feature for something you build for users; fixes, chores and research get no PRD.
  2. Premises. The lead writes down what it assumes, as premise cards. You see them on the page and tap yes or no.
  3. The PRD (feature rooms only). The lead drafts PRD.md: purpose, goals and non-goals, numbered testable requirements, definition of done, 120 lines at most. While it drafts, only research items may run. When it's ready you get an “Agree the PRD?” card; agreeing opens building.
  4. The plan. The lead adds one item per piece of work, each with acceptance lines, inputs, dependencies, a cap in hours and a model tier. Items with no dependency between them run in parallel.
  5. Workers. rooms spawn export T03 --repo ~/code/app gives the item its own worktree and branch, a scratch folder, and a background session on the item's tier. The worker logs as it goes and finishes with rooms done, which tells the lead.
  6. Your part. Cards arrive on the page, most blocking first. Tap an option; you have a few seconds to undo. The receipt says when the lead has read it. You can also type D05 b to the lead in chat; it is recorded before the lead reads it.
  7. Closing. When the definition of done holds and the work is merged, the lead runs rooms close export "shipped in 1.4". Follow-up work gets a new room.

At any time, rooms status shows every room, and rooms chat export opens the room's lead in your terminal.

Who gets asked what

Only decisions that are yours reach you. The lead chooses the kind; the command routes it.

KindExampleReaches you as
Hard to undoa public name, an API field, merging to main, a deploy, spendinga card with options and the team's pick
Reversible but worth knowingscope or order of work“going ahead unless you stop it”, with a time; it applies itself if you don't
Premise“the export runs on the existing job queue”a yes / no card
Something only you can docreate an API token, approve an accounta task with exact steps and a Done button
Free-text answera name, a datea text box
Engineering choicewhich index typenothing: the team decides and writes it down

On any card you can ask a question instead of answering; the card waits until the lead replies.

Where it runs

A room runs on one machine: its lead and worker sessions, the records in ~/rooms, and rooms serve. That can be your laptop (rooms pause while it sleeps; nothing is lost) or an always-on host, where rooms keep moving while you are away.

Never run the same ~/rooms on two machines at once: event inboxes and the session list are local, so two hosts would each start their own lead turns. A git remote is a backup and a way to read records elsewhere, not a sync.

From another machine, toDo
Answer cards, pause, wake a leadopen the page over your tailnet
Talk to a room's leadssh host -t rooms chat <room>
Work in the roomsssh host -t 'cd ~/rooms && claude'
Chat with a lead from claude.ai/code or the appstart it on the host with claude --remote-control lead-<room> in ~/rooms, then rooms lead <room> inside it

How the lead hears things

Taps, finished items, needs and due defaults become events in the room's inbox. If the lead session is open with the plugin, it takes them between tool calls (no extra turn) or as one prompt when idle. If no lead is running, a one-shot lead turn (claude -p in ~/rooms) handles them and exits. A running session is never resumed from outside, because that would fork it.

Records

Every record is a markdown file: key: value lines between --- markers, then ## Section bodies. Edit them freely; the commands keep the rest in step.

~/rooms/<room>/
  BRIEF.md              charter and wiring
  PRD.md                feature rooms only
  now-head.md           the lead's current position
  items/T01-*.md        work items
  decisions/D01-*.md    decisions (D), premises (P), asks and tasks (A)
  refinements/RF01-*.md changes to an agreed PRD
  notes/                long-form notes, one writer per file

BRIEF.md

FieldMeaning
titlethe room's name for people
lead_sessionthe Claude Code session id of the lead; events go to it
sessionsearlier or extra lead sessions
repos, codeproduct repos, and the integration branch and its worktree
pauseda time when you paused it; empty when running
closeda time and one-line outcome; set by rooms close

Sections: Goal, Premises, Scope, Team (one charter per member), Where things are.

now-head.md

phase (one line on where the room is), since (your last message), waiting and resume (an outside wait: who or what, and when it picks up again). The body is a short note to you.

PRD and refinements

The PRD's status is draft, review or agreed; building is locked until it is agreed. An agreed PRD is never edited: a change is a refinement (status draft, review, agreed or superseded; touches lists the requirement ids it changes). The binding set is the PRD plus its agreed refinements, in order; rooms brief <room> prints it.

CommandDoes

rooms help lists every flag. Set ROOMS_AS=<name> so log lines carry it.

Configuration

~/.config/claude-rooms/config.json, all optional:

{
  "tiers": {
    "light":    { "model": "claude-haiku-5-5",  "effort": "medium" },
    "standard": { "model": "claude-sonnet-5-5", "effort": "medium" },
    "review":   { "model": "claude-opus-5-5",   "effort": "high" }
  },
  "worker": { "permissionMode": "auto", "tier": "standard" },
  "lead":   { "permissionMode": "auto", "allowedTools": ["Bash(rooms *)", "Read", "Edit", "Write"] },
  "provisionalMinutes": 60,
  "commitDebounceMs": 60000
}
  • Tiers: light for mechanical work, standard for ordinary implementation, review for judging someone else's work. Deeper models only when you ask for them: pass --model to rooms spawn.
  • Permission modes: workers and one-shot leads run unattended, so a mode that asks for permission leaves them waiting with nobody to answer. Keep a mode that doesn't prompt, and narrow the lead's allowedTools if you want it to touch less.
  • provisionalMinutes: how long a reversible call waits before it goes ahead (30 at least).

Troubleshooting

Every room has one status: needs you, stuck, moving, waiting outside, paused, idle or done. rooms status <room> gives the reason and, under “For the lead”, what to fix.

You seeIt meansDo
Stuck: items are ready but nobody is working on themthe lead ended its turn without starting worktap Wake the lead on the page, or rooms tell <room> "dispatch the ready items"
Stuck: Tnn finished without reporting backa worker's turn ended with its item still doingthe lead has been told; if nothing happens, read the item's Log and rooms tell <room> "…" --item Tnn
Stuck: updates for the lead can't reach itthe lead session is open without the plugininstall the plugin (above) and /reload-plugins in that session
Tnn doing, but its worker is idlethe worker stopped, often on a permission promptclaude attach <id> to see it; set a permission mode that doesn't prompt
rooms spawn --lead fails with “workspace not trusted”background sessions need the folder trusted oncerun claude in ~/rooms once and accept the prompt
A command refuses: “the PRD is draft”building is locked until you agree the PRDonly research items run before; the lead asks with rooms prd <room> review
Mirror push failingthe background push to your remote erroredcheck credentials on the host; records are safe in the local repo
Nothing on the page updatesrooms serve isn't runningsystemctl --user status claude-rooms
